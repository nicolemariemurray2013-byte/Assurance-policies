## 1. Purpose and method of resource identification

This register **identifies and documents the resources required for activities at each AI system
life-cycle stage** and for other AI-related activities relevant to the organization. Resources are
identified at three trigger points: (a) at inception of any new AI system, (b) at each quarterly
review, and (c) on any material change (new model, new data source, new tool, new dependency).

Resources are recorded **regardless of who provides them** — the organization, its customers, or
third parties — because inherited resources carry inherited risk. Each entry below names the
provider explicitly.

### 3.2 Categories, roles and intended use of data

| Category / role | Data | Intended use |
|---|---|---|
| **Training** | None | The organization performs no model training or fine-tuning |
| **Validation** | Evaluation regression corpus (labelled subset, 30%) | Tuning prompts, rubrics and thresholds during development |
| **Test** | Evaluation regression corpus (held-out subset, 70%, never used for tuning) | Pre-release verification and validation of evaluation accuracy |
| **Production (inference input)** | Customer evidence documents; AWS configuration scan records | Producing a compliance verdict for the customer's control |

| **Operational telemetry** | Event logs, traces, metrics | Traceability, monitoring, incident investigation |

### 3.3 Labelling and data preparation processes

- **Labelling.** Regression-corpus items are labelled with the expected per-requirement verdict by
  two qualified compliance analysts independently; disagreements are adjudicated by the Responsible
  AI Lead. Inter-rater agreement is recorded per labelling round (last round: 0.94 Cohen's kappa).
- **Preparation.** Customer evidence is decoded, content-type validated, classified by evidence type,
  and normalized to text before analysis. Scan records are normalized into a documented
  `ScanEvidence` structure grouped by account and region, preserving the verbatim API response so a
  verdict can always be traced back to the raw observation.
- **De-identification.** Historical assessments entering the regression corpus have customer
  identifiers, account numbers and resource ARNs replaced with stable synthetic tokens.
- **Exclusion.** Evidence that fails an integrity check is rejected rather than repaired, and is
  never silently substituted.

### 3.4 Data quality characteristics, retention and disposal, and known bias

**Quality characteristics tracked:** completeness (does the evidence bear on every requirement),
accuracy (does the extracted claim match the source text), timeliness (scan freshness — scan
evidence is always collected fresh and never reused across assessments), consistency
(inter-run agreement on identical inputs), and traceability (every verdict cites its source excerpt
or raw API record).

**Retention and disposal:**

| Data | Retention | Disposal |
|---|---|---|
| Customer evidence documents | For the life of the customer agreement + 7 years (audit-record obligation) | Deleted on documented customer request or at retention expiry, via the evidence-store deletion workflow |
| Assessment results and per-requirement verdicts | 7 years | Automated expiry |
| Scan evidence | Retained with the assessment it supports; never reused as current evidence for a later assessment | Automated expiry with the assessment |
| Operational event logs | 400 days minimum | Lifecycle expiry |
| Regression corpus | Until superseded; reviewed annually for continued relevance | Deleted when superseded |

**Known or potential bias issues:**

1. **Document-style bias** — verbose, well-formatted policies risk scoring better than terse but
   equally compliant ones. Mitigation: rubrics score on the presence of required elements, not
   length or polish; the regression corpus deliberately includes terse compliant documents.
2. **Service-coverage bias** — scan coverage is richer for long-established AWS services than for
   newer ones, which can under-credit accounts built on newer services. Mitigation: a requirement
   the scan cannot read is treated as a coverage gap resolved by documentation, never as a failure.
3. **English-language bias** — evaluation quality is best characterized for English-language
   evidence. Mitigation: documented as a technical limitation; non-English evidence is routed to
   human review.
4. **Recency bias in the corpus** — the corpus over-represents recent frameworks. Mitigation:
   annual rebalancing review.

## 4. Tooling resources

### 4.1 Algorithms, models, data conditioning, optimization and evaluation methods

| Tooling category | What is used |
|---|---|
| **Algorithm types** | Large-language-model inference within a directed multi-node evaluation graph; deterministic rule-based scoring of per-requirement statuses; no gradient-based training |
| **Machine learning models** | Anthropic Claude Sonnet (context gathering, scanning, analysis nodes) and Claude Opus (auditor node), accessed via Amazon Bedrock; model identifiers are configuration, recorded per release |
| **Data conditioning tools / processes** | Evidence decoding and text normalization; evidence-type classification; scan-record normalization into the documented `ScanEvidence` structure; de-identification pipeline for corpus entries |
| **Optimization methods** | Prompt and rubric optimization against the validation split, with the test split held out; no model weight optimization. Changes are accepted only on a measured, non-regressing test-split result |
| **Evaluation methods** | Per-requirement verdict accuracy against labelled ground truth; precision/recall on gap detection; run-to-run consistency on identical inputs; adversarial and prompt-injection test suites; deterministic scoring-formula unit tests |

## 5. System and computing resources

**Resource requirements.** The evaluation workload is inference-bound rather than compute-bound: a
single control assessment consumes on the order of 1–3 vCPU-minutes of container compute, under 2 GB
of memory, and is dominated by foundation-model inference latency (typically 75–150 seconds
end-to-end per control). Peak demand is driven by framework-level assessments that fan out across
controls and accounts.

**Where the resources are located.** All AI system computing resources are **cloud computing**, in
AWS account 471885797689, region us-west-2. There are **no on-premises and no edge computing
resources** in scope: no model runs on customer premises or on end-user devices.

| Resource class | Implementation | Location |
|---|---|---|
| Compute (agent runtime) | Bedrock AgentCore managed container runtime | Cloud — AWS us-west-2 |
| Model inference | Amazon Bedrock managed endpoints | Cloud — AWS us-west-2 |
| Storage | Amazon S3 (evidence store and staged scan evidence); Amazon DynamoDB (assessment, journal, lock and coordination records) | Cloud — AWS us-west-2 |
| Network | Amazon VPC with private subnets and VPC endpoints for AWS service access; TLS in transit throughout | Cloud — AWS us-west-2 |
| Asynchronous messaging | Amazon SQS (metering and dispatch) and Amazon SNS (notification) | Cloud — AWS us-west-2 |
| Analytics | Amazon Athena workgroup over assessment history | Cloud — AWS us-west-2 |
| Security monitoring | AWS CloudTrail (API activity), Amazon GuardDuty (threat detection) | Cloud — AWS us-west-2 |

**Relevant impacts of the hardware used to run AI workloads.** Inference runs on AWS-managed
accelerated hardware whose specification is not exposed to or controlled by the organization; the
practical impacts we track and manage are: (a) **energy consumption and greenhouse-gas emissions**
attributable to inference, which dominate the AI system's environmental footprint and are reported in
the societal impact assessment; (b) **shared-tenancy performance variability**, which can lengthen
assessment latency and is absorbed by asynchronous invocation rather than by user-facing timeouts;
(c) **regional capacity constraints** for specific models, mitigated by a documented fallback model
configuration; and (d) **no hardware disposal obligation** for the organization, since all compute is
provider-managed — e-waste and hardware end-of-life sit with AWS under the shared responsibility
model.
