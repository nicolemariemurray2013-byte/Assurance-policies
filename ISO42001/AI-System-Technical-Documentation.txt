## 1. Technical documentation needed for each category of interested parties

The organization has **determined what technical documentation each relevant category of interested
party needs, and the appropriate form in which it is provided.** Need is determined by what each party
must decide or do, not by what happens to be written.

| Interested-party category | What they need it for | Documentation provided | Form provided in |
|---|---|---|---|
| **Assessed organizations (customers / users)** | Decide whether to rely on a verdict; understand purpose, limits and their obligations | System overview and intended purpose, usage instructions, technical limitations, monitoring and influence capabilities (§2) | Customer-facing product documentation portal and in-product help; plain language, no internal identifiers |
| **Compliance analysts and auditors (operators, human oversight point)** | Review, explain and override verdicts | §2 plus rationale interpretation guide, evidence-citation model, override procedure, the assessment journal | Operator guide plus the in-product journal view; worked examples |
| **External auditors and certification bodies** | Obtain assurance over the AIMS and this system | Design and architecture (AIMS-DOC-009), V&V records (AIMS-PLAN-010), impact assessments, deployment records, event logs | Controlled evidence pack, released on request under NDA; document IDs and versions cited |
| **Regulators / supervisory authorities** | Verify legal obligations | Intended purpose, data categories and provenance, impact assessment, human oversight, logging and retention | Regulatory dossier assembled from the register in §4 |
| **Operations and on-call engineers** | Run, monitor and repair the system | Runbook, alarm catalogue, failure-management and health-monitoring processes, SOPs, roles, update documentation (§3) | AIMS-PRO-007 runbook plus alarm and dashboard definitions |
| **Developers and reviewers** | Change the system safely | Architecture, design choices, interface and tool contracts, data-quality assumptions, test strategy | In-repository technical docs and AIMS-DOC-009, versioned with the code |
| **Security reviewers** | Assess and re-assess threats | Threat model incl. AI-specific threats, trust boundary, credential and data-flow documentation | AIMS-DOC-009 §6 plus the security review record |
| **Model and infrastructure suppliers** | Support and capacity | Usage profile, model identifiers, region, throughput and quota needs | Supplier engagement record (AIMS-PRO-010) |
| **Internal management and the AIGB** | Govern and authorize | Impact assessments, release authorizations, performance and incident reporting, exceptions | Governance pack for the quarterly AIGB review |
| **The organization's own employees who use results** | Understand what a score does and does not mean | Intended purpose and limitations, out-of-purpose statement | Internal enablement material |

Access is role-appropriate: customer-facing documentation excludes internal infrastructure detail, and
prompts and rubrics are withheld as intellectual property (AIMS-DOC-009 §6) while the rationale behind
every verdict is always disclosed.

## 2. Core AI system information

| Element | Content |
|---|---|
| **General description** | An orchestrated, five-node inference graph that assesses an organization's compliance with a managed control framework using foundation models on Amazon Bedrock. It gathers scope and evidence, reads the customer's cloud environment read-only, analyses supplied documents, and produces a per-requirement verdict with a cited rationale and a control-level score. Architecture in AIMS-DOC-009 §2. |
| **Intended purpose** | Automated, evidence-cited compliance assessment of an organization's own environment and documentation against a supported managed framework, to support — never replace — qualified human compliance judgement. Out-of-purpose uses are listed in AIMS-PRO-007 §7.1. |
| **Usage instructions** | Register the environment and establish the read-only trust relationship; create a project and select the framework; upload evidence documents and link them to the specific controls they support (an unlinked document is not visible to a control); run an assessment at control or framework level; review per-requirement verdicts with their cited evidence; annotate or override; act on the requirement-tied remediation tasks. Evidence must be a supported content type, with the declared type matching the file. |
| **Deployment assumptions** | Cloud-only on the managed container runtime in us-west-2; no on-premises or edge deployment. Assumes the supported model identifiers are available in-region with sufficient quota; that the customer has established the cross-account read-only trust relationship; that supporting storage, queue and record stores exist and are reachable; and that the front-end control plane is contract-compatible. Full development-versus-deployment differences in AIMS-PLAN-008 §3. |
| **Operation assumptions** | Machine-invoked, asynchronously, one assessment at a time per assessment record (a lock serializes it) while the platform scales out across assessments. Assumes evidence supplied is the customer's own and lawfully held; that scan reads are authorized; and that a qualified human reviews consequential verdicts. |
| **Technical limitations** | (a) Accuracy characterized only within the documented domain of use — English-language evidence, supported managed frameworks (AIMS-PLAN-010 §3.2); (b) a scan can only observe what the underlying APIs expose, so process, human and outside-AWS controls must be evidenced by document; (c) verdicts are probabilistic model judgements, not deterministic tests — only the score arithmetic is deterministic; (d) a result is a point-in-time observation, not continuous monitoring; (e) not a certification or attestation; (f) unreadable evidence yields an explicit read-failure state, not a compliance verdict; (g) supplier model behaviour can change beneath a model identifier, so results are reproducible only in conjunction with the recorded model identifier and version. |
| **Monitoring capabilities and functions that let users or operators influence operation** | Users and operators can: read the assessment journal (every phase, tool call and intermediate result); see per-requirement rationale and cited evidence; distinguish an evidence gap from a failure in the output; **override** any verdict; annotate; **halt or re-scope** an assessment; add or replace evidence and re-run; suspend the system entirely (AIGB authority); and view health, latency, error-rate and verdict-distribution dashboards. Operators additionally control the model identifier and the enabled framework set as configuration. |

## 5. Accuracy, currency, approval and procedures for operational change

**Accuracy and currency.** Documentation is updated **in the same change as the system change it
describes**; a change whose documentation is not updated fails peer review, and documentation currency
(RC-10) is a release criterion that blocks release. Every document carries an owner, a version, an
approval and a review date; an out-of-date document is a nonconformity raised in the AIMS
corrective-action log.

**Approval by relevant management.** Technical documentation is approved by the AI System Accountable
Owner; responsible-AI content additionally by the Responsible AI Lead, security content by the AI
Security Lead, and policy-level documents by the AIGB. Approvals are recorded in §4.

**Procedures to address operational changes.** Every operational change is classified (Minor,
Standard, Material, Emergency — AIMS-POL-006 §4). The classification determines the documentation,
regression and communication obligations:

| Step | Requirement |
|---|---|
| 1. **Internal evaluation of the type of change** | The AI Development Lead proposes a class; the AI Operations Lead and, for anything verdict-affecting or oversight-affecting, the Responsible AI Lead confirm it. Material classification re-triggers the impact assessment. Classification is recorded with the change and is auditable — a change may be reclassified upward in review, never downward without Responsible AI Lead agreement |
| 2. Documentation update | Affected documents in §4 updated and re-approved in the same change |
| 3. Verification | Regression scope per the class (AIMS-PLAN-010 §2) |
| 4. **Communication to users** | Per the matrix in AIMS-PRO-007 §5.2 — verdict-affecting changes announced at least 10 business days ahead with their effective date and expected effect; documentation published before or with the change, never after |
| 5. Post-change confirmation | AI Operations Lead confirms the deployed system matches the documentation; discrepancy is a defect |
